# 对照实验：省略主语的追问，需不需要 query 改写？

**结论：不做。** 当前语料规模下改写**不改变命中、只提高分数**，不值得为它多付一次模型调用与一次往返延迟。
触发条件：语料变大后 top1 真开始失准，再回来做。

一次性对照脚本**未入库**（它会在库里建临时知识库、调 embedding，不适合留在仓库里当测试跑）。
本文件保留**语料、追问清单、方法与结果**，够复现也够讲清楚。

---

## 1. 要回答的问题

RAG 问答里有一类问法是天然依赖上文的：

```
第 1 轮：年假可以休几天？
第 2 轮：那病假呢 / 它有几天 / 需要提前几天申请 …
```

历史虽然会拼进 Prompt，但**检索用的是第 2 轮那句话本身**。所以"它有几天"这种句子拿去检索，
字面上几乎没有信息量。query 改写要做的事就是"先用历史把它补全，再拿去检索"。

**但它值不值得做，完全取决于一件经验事实：补全后的句子在 Milvus 里能不能命中更好的 chunk。**
这件事 10 分钟能测出来，所以先测，而不是先开发。

---

## 2. 对照口径（这里有三个坑，都踩过）

| 项 | 取值 | 为什么 |
|---|---|---|
| 接口 | `POST /api/search` | 纯检索，不烧 LLM token，可以放心多跑几组 |
| `rerank` | **必须显式 `true`** | `/api/search` 默认 `false`（纯向量），而 `/api/chat` 默认**开重排**。不对齐就变成"拿纯向量 top1 去推断问答用的 top1"，结论不能外推 |
| `kb_ids` | **必须限定到实验库** | 不传 = 用户所有可访问库；而 admin **不受限**（`get_accessible_kb_ids` 返回 `None`），干扰项和别的库全会进来 |
| 限流 | 用**环境变量**临时关掉 | `RATE_LIMIT_ENABLED=false`，不动 `.env` |

对照组设计：同一句追问跑两次 —— **原话**（现状行为）与**人工补全的话**（模拟改写的上限）。

---

## 3. 语料：第一版是错的（这一节是本文最有价值的部分）

### 第一版：3 篇文档 → 假绿，作废

放了《员工手册》《差旅制度》各一篇 + 一篇干扰项，每篇约 300 字（刚好各 1 个 chunk）。

| 指标 | 结果 |
|---|---|
| 原话 top1 正确 | **16/16** |
| 改写 top1 正确 | 16/16 |

看着像"检索很准、不需要改写"——**但这是假绿**。铁证：

```
追问「它有几天」→ rerank 分 0.0016（几乎不相关）却仍然排第一
```

3 个 chunk、另外两个还跑题，检索已经退化成"3 选 1 挑主题"。**0.0016 的分数在真实语料里会排到末尾**，
在这里却拿了第一 —— 靠的是排除法，不是理解。

> **教训：对照实验的语料必须有区分度。** 语料太小时，正确答案会被"别人的相关性更差"顶上来，
> 于是任何方法都显得够用。

### 第二版：8 篇同质文档（有效）

8 篇主题各不相同、但**用词高度重叠**的文档（全都含"申请 / 审批 / 天 / 需 / 提交"），
让"正确答案是 8 个里挑 1 个、且分差不大"成为常态：

`年假规定` `病假规定` `婚假规定` `加班调休规定` `考勤打卡规定` `差旅报销规定` `出差申请规定` `办公用品采购流程`

每篇 200~300 字（各 1 个 chunk）。以《年假规定》为例：

```
年假规定

员工入职满一年可享受带薪年假 5 天；满三年 10 天；满五年 15 天。
年假需提前 3 个工作日通过人事系统提交申请，由直属主管审批后报人事部备案。
年假当年有效，未休完的不结转至下一年度，也不折算工资。
```

（完整 8 篇见实验脚本；其余各篇结构相同、主题分别是病假 / 婚假 / 调休 / 考勤 / 报销 / 出差申请 / 办公用品。）

## 5. 判定线与结论

**事前定死的判定线**（避免事后找理由）：

```
有效样本 = 原话判错的组数（只有这些组，改写才有机会"纠对"）
   有效样本 < 5      → 说明"原话本身就不怎么失准"，这个功能没有受众 → 不做
   纠正率 ≥ 50%      → 值得做
   纠正率 ≤ 20%      → 不做
   两者之间          → 单独讨论
```

本次结果：**有效样本 = 1，远低于 5** → **不做**。

⚠️ 说清楚这个结论的强度：它说明的是"**当前这种小语料下，省略主语的追问并没有把 top1 弄错**"，
**不是**"改写没用"。所以 README 里那行写的是"这个实验**不足以证明**改写有价值"，
而不是"改写没能提升命中率"——13/14 到 14/14 本身就是多了 1 组，措辞不能自相矛盾。

**真正稳定成立的差别在分数，不在名次**：

```
ctx 组原话 top1 分数：0.0074 ~ 0.24（多数 < 0.15）
同一组改写后：        0.66 ~ 0.99
```

即"**名次对了，但依据几乎为零**"。语料一变大，这些接近 0 的分数就会被别的 chunk 挤下去。
这也解释了为什么第一版（3 篇文档）是假绿。

---

## 6. 顺带产出（以及它没能产出什么）

这 28 个 `(问题, top1 分数)` 数据点**不能**用来定 `RAG_MIN_SCORE`：
它们全是"库里有答案"的**正样本**，而阈值需要的是"明明库里没有答案"时分数能到多高的**上界**。
要定阈值必须造**负样本**（明知库里没有的问题），这是另一件事。

## 7. 环境与复现

前置：MySQL 可用；Milvus VM 已开机；embedding key 已配。

```bash
# 复现要点（脚本是一次性的，未入库，需要自己照这个流程写一个）：
#   1. 建一个临时知识库，灌上面 8 篇文档，等解析完成后向量化
#   2. 对 14 组追问，各跑两次 POST /api/search：
#        {"query": <原话 或 人工补全>, "kb_ids": [<临时库 id>], "top_k": 5, "rerank": true}
#   3. 比 top1 的 document_name 是否等于表中的"正确来源"
#   4. 删库收尾（级联清文档 / chunk / 向量 / 磁盘文件），并确认 Milvus 计数归零

# 用环境变量临时关限流（不动 .env）—— 否则 28 次 search 会撞 RATE_LIMIT_SEARCH_PER_MINUTE=60
RATE_LIMIT_ENABLED=false python <你的脚本>.py
```

实验数据已确认清干净：MySQL `documents` / `document_chunks` 归零、`uploads/` 空、
Milvus `document_chunks` 计数为 0。
